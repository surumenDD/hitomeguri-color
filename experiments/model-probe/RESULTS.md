## 見た目（メインの目視）

一覧画像は `results/*.jpg`（左上から 起動1秒後・12秒後・ドラッグ直後・ドラッグ4秒後）。

- **Codex**: 緑・青緑・ピンク・紫の色面。なめらかで、差し込んだ色はにじんでから場になじむ。仕上がりは一番良い。ただしパレットは「よくあるグラデーションの壁紙」に寄り、緑が重い。題字と操作の案内まで作り込んでいた。
- **MiMo**: 薄紫・セージ・藤色の低彩度。落ち着いているが全体に灰色がかり、右下がくすんだオリーブになる。差し込んだ色が4秒後に画面の半分近くを覆い、「なじむ」より「上塗り」に近い。
- **DeepSeek**: 深緑・オリーブ・えんじ・薄紫・青緑の塊。塊の境目が灰色に濁る。補色どうしを OKLab で混ぜた中間が灰色になるのは計算として正しいが、配色の選び方でそれを避けていない。

## 仕事の進め方

- **Codex**: 自分で Playwright を使い、スクリーンショットを画像として見て確かめた。色域変換の値（#00be58、C=0.1928）はメインの独立計算と一致。確かめていないこと（file: での起動、ほかの GPU、実機のタッチ）を正確に書いた。作業ツリーに Playwright MCP のログができたとき、範囲外として自分で消さずにエスカレーションした。一方で、確認用の HTTP サーバーを止めずに完了報告した（メインが停止）。
- **MiMo**: selftest の数値は Node で、描画は Edge の headless で確かめた。画像を見られず（dsh が画像入力を宣言していない）、ドラッグ・Space・S・reduced motion を自分で確かめられなかったと正直に書いた。
- **DeepSeek**: Python の独立実装で selftest を照合し、CDP で実 GPU のフレーム時間と画素の統計を測った。画像を見られないため、見た目は数値からの推測だと書いた。

## 割り振りへの示唆

- 見た目の質が問われる仕事（作品の画面、シェーダー、色の設計の実装）は Codex に振る。自分で画面を見て直せるのは、3者のうち Codex だけだった。
- dsh の2モデルは、公式には画像入力に対応している（`docs/research/model-survey.md`）。それでも dsh 経由では画像を読めなかったので、見た目の確認はメインが `tools/visual-qa` で引き受ける前提にする。
- 数値の正しさと検証の手堅さは、3者とも十分だった。見た目の判断を伴わない仕事（色の計算のライブラリ、テスト、データ処理、ツール）は、安い dsh の2モデルに振れる。
- コードの読みやすさは今回は採点していない。最初の本番タスクのレビューで見る。
