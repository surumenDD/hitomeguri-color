# パレット差し替えの試作

作成日: 2026-10-27。読む人: ADR-0003 の「画像の細部を壊さずに色を巡らせられるか」を判断する設計者・実装者。

## 判断

**次の試作には、固定した柔らかい重みと残差を使う方式を勧める。** 4枚とも元のパレットでは元画像を完全に再現し、大きな色相変更でも最近傍の境界による斑点を抑えた。前処理は約0.31秒、1080pの単一画像の合成は今回のGPUで約0.10〜0.20msだった。

これは製品用の分解方式を確定する結論ではない。柔らかい方式は編集が隣の色にも広がり、指定色への変化も薄まる。残差が元画像の情報を保持しているので、画像全体を8色だけに圧縮できたわけでもない。次は、編集する島の固定・手直しと、パレットの各色を狙いどおりに動かす重みを検証する必要がある。

硬い量子化は不採用。8色に減らすだけでは、写真の雲・水面、絵画の筆致、ポスターの空の階調が壊れる。最近傍への残差追加は比較用に残すが、大きな単色変更で空と水面に斑点が出るため既定にはしない。

## 比較した計算

画素の元のOKLab値を `x`、抽出した色を `P[k]`、編集後を `Q[k]`、最近傍の番号を `n(x)` とする。色数は全画像・全候補で **8**。画像を原寸でsRGBにデコードし、ブラウザのWeb WorkerでOKLabへ変換する。32768画素の決定的な等間隔標本に、最遠点で初期化したk-meansを最大20回適用した。同距離の場合は先の番号を採る。全画素の最近傍を計算して面積順に並べ、最大の色を番号0に固定する。

| 候補 | シェーダに渡す表現と再合成 | 保持する情報 |
|---|---|---|
| 硬い量子化 `hard` | `y = Q[n(x)]` | 最近傍の番号だけで表せる。失敗の基準 |
| 差分を保つ `residual` | `y = x + Q[n(x)] - P[n(x)]` | 番号と元のOKLab値。残差 `x-P[n(x)]` を保持 |
| 柔らかい重み `soft` | `y = x + Σ w[k](x) (Q[k]-P[k])` | 元のOKLab値と8つの重み。残差 `x-Σw[k]P[k]` を保持 |

柔らかい重みは `w[k] ∝ exp(-||x-P[k]||²/(2σ²))`、非負で総和が1。σは各パレット色から隣の色までの距離の中央値の0.8倍を、0.035〜0.12に収める。画像別のσは `metrics.json` の `images[].sigma` にある。これは色空間内の連続なGaussian RBFであり、位置・物体・マスクは使っていない。

パレット・最近傍の番号・重みを、色の編集や再生中に計算し直さない。残差を使う2方式では `Q=P` のとき代数的に `y=x` となる。残差を明示的に別テクスチャに置かず、元画像とパレットの差分からシェーダで合成する。前処理したOKLab+番号と重み2枚を `RGBA32F` テクスチャに、元のパレットと編集中のパレットを `vec3[8]` uniform に置く。表示はWebGL2のフラグメントシェーダで行う。表示用に4個のコンテキスト、検査には別の1個を使う。

### 論文との関係

- [Changら2015・著者のプロジェクトページ](https://pixl.cs.princeton.edu/pubs/chang_2015_ppr/index.php): LAB上の滑らかな色転送をRBFで組み立て、色域と明るさの順序にも対応している。本試作はこの完全な実装ではなく、固定・正規化したGaussian重みと残差を使った比較候補である。パレット色での補間制約や輝度の単調性を保証していない。
- [Tanら2018・著者のプロジェクトページ](https://cragl.cs.gmu.edu/fastlayers/): RGBXYの幾何から空間的に整った加算混合層を求める。本試作は「固定した加算混合の重みで再合成する」という表現を参考にしたが、5次元の凸包・Delaunay分割・パレット抽出は実装していない。色のk-meansも共通条件として残している。したがって、この結果でTanの手法の性能・品質を評価したとは言えない。

原文は `~/research/palette-recoloring/sources/` にあるChangおよびTanのテキストを参照した。論文・他人の画像・実装コードはこのフォルダへ転載していない。

## 共通の色替え試験

- **a: 恒等変換**。抽出したパレットをそのまま返し、原寸で描画する。元画像のデコード済みsRGBバイト列と比較する。
- **b: 最大の色だけを変更**。最近傍の割り当て面積が最大の色のOKLCH色相を+120°回す。LとCを保ち、色域外ならLと色相を保ってCを下げる。他の7色は変えない。
- **c: 夕方→残照→夜→夜明け→夕方**。各画像のパレットから同じ規則で4つのキーを作る。区間の長さは3:1:2:1、全長20秒。キーの時刻は **0、8.571429、11.428571、17.142857秒**。隣のキーをOKLabの直線で混ぜ、進行には `u²(3-2u)` を使う。位置・速度が周回の境目でもつながる。

台本のキーは `color.js` の `scriptKeys()` にある。各キーで、Lを `scale × L + offset`、色相と彩度を順に `(24°,0.85倍)、(-18°,0.72倍)、(-38°,0.58倍)、(10°,0.70倍)` にする。Lの係数は順に `(0.94,0.018)、(0.80,0.06)、(0.65,0.09)、(0.98,0.006)`。暗い色をわずかに持ち上げ、明るい色を落として夜のコントラストを圧縮する。物体や光源を理解する台本ではない。

色域外の出力は、Lを固定したままa,bを同じ倍率で縮め、18回の二分探索でsRGBに収める。RGBを単純に切り捨てる処理は使わない。浮動小数点の誤差として線形RGBの±0.000001を許す。Lそのものが0〜1の外に出る場合は彩度だけでは解決できないので、診断で数える。本試験のa・b・cでは全候補・全画素のLが範囲内だった。cの出力Lはキー間の凸補間なので、原寸で4キーを検査すれば区間内も範囲内と分かる。

## 測定条件

実測環境はWindows、Chrome **155.0.8059.86** のheadless、WebGL2、ANGLE/D3D11、**NVIDIA GeForce RTX 5070 Ti**、DPR 1。2026-10-27 01:32 JSTの実行。CPUの論理並列数は16。数値は単発の試作計測であり、他端末、低性能GPU、スマートフォンの保証ではない。

- **PSNR**: `10 log10(255²/MSE)`。MSEは原寸の全画素・RGB全チャンネル、sRGBの8bit値で計算する。アルファは含めない。∞は誤差0で、単なる桁丸めではない。元画像は1536×1024、にせのドット絵だけ1672×941。比較の基準はブラウザがPNGからデコードしたsRGBで、PNGの圧縮前データやICC変換の検証ではない。
- **前処理**: Worker内の色変換、パレット抽出、全画素の最近傍と並べ替えまで。softにはさらに全画素の重み計算を含める。hardとresidualは同じ前処理を共有するので同じ値。画像の取得・PNGデコード・Worker起動・GPU転送は含めない。これらを含む時間も `images[].loadAndProcessMs` に別途記録する。
- **描画**: 同じ原寸テクスチャから1920×1080のバッファ全面へ描画。原画のアスペクト比を保つ余白は入れず、全画素で計算する。パレットはa、b、cの4キーを交互に使う。12回ウォームアップ後31回測り、`EXT_disjoint_timer_query_webgl2` のGPU時間の中央値を示す。disjointが出た標本は採用しない。同期の壁時計時間もJSONに記録した。GPU値は単一画像のシェーダ合成で、4画像×4列のページ全体、レイアウト、合成・表示待ちを含むフレーム時間ではない。
- **フレーム差**: 実際の同じシェーダを、画像全域に対応する192×128、にせのドット絵は192×108の固定グリッドに描画。60fps相当の `t=0,1/60,…,20` をオフラインで全1201フレーム描き、1200組を比較する。GPUが出力した8bit値を読み、`D(t)=mean(|R₂-R₁|,|G₂-G₁|,|B₂-B₁|)` を求める。最大・中央値の単位は **0〜255の1チャンネル分の値**。20秒→0秒のループの接続も含む。実時間20秒の動画や、原寸全画素での時間差検査ではない。疎な細線のちらつきは見逃し得る。

## 時間の連続性

パレット側のステップは `S(t)=max_k ||Q_k(t)-Q_k(t-1/60)||₂` （OKLab）。出力との比は `G(t)=D(t)/(255 S(t))` とし、ゼロ付近の割り算を避けるため `S≥0.00001` の組だけを集計した。これは異なる単位の値の比であり、1を合否の閾値にはしない。8bitの丸めも含む。全フレームのDとSをJSONに残している。

**測定した範囲では、割り当ての切り替わりによる大きな瞬間的ジャンプはなかった。** そもそもこの3方式では番号・重みが変わらない。色域変換前は、hardとresidualはパレットの1色の移動、softはその凸結合なので、各画素のOKLabステップは必ず `S(t)` 以下になる。これは時間方向の割り当て変更を排除する性質であり、空間の境界がきれいなことの保証ではない。

硬い量子化はGの最大が大きい。出力が8色しかないので、同じ色の広い面が8bitの境を同時に越える。1画素の最大差は1だが、原画の約45%を占めるポスターの色の島が一緒に変わるため、平均Dは最大0.416まで上がった。低速の部分でGが大きくなり、中央値が小さいのはこの段階的な更新のためで、領域の再割り当てが発生した証拠ではない。

柔らかい方式のD最大は全画像で残差方式より小さかった。ただし編集そのものの弱まりも含むので、この数字だけで品質が高いとはしない。にせのドット絵の局所最大は4、残差方式では5となり、彩度の強い看板で色域変換の影響が残る。softの試験bでは約16.2%の画素が彩度圧縮を受けた。他の画像ではbで0.001〜0.45%程度。クリップして質感を潰す代わりに彩度を下げる方針だが、彩度・色の関係は変わる。

## 残る問題と次の判断材料

1. **狙った色への到達と局所性**。正規化したGaussianはパレット色そのものでも他色の重みが0にならない。softのbは表示したパレットどおりに全面が+120°回るわけではない。次はパレット色での補間制約を持つRBF、または幾何に基づく重みと並べる。色を強く変える公平な比較には、同じパレット変更に加えて実際の色の移動量も合わせる必要がある。
2. **物体の島ではない**。色だけで分けるため、同じ青の空・海・建物を別々に操作できない。写真の淡色と光源も巻き込む。TanのRGBXYや領域マスクを次の候補にし、使い手が島を固定・分離できることを検証する。
3. **残差と大きな変更**。aの完全再現は残差の性質であり、b・cで階調の順序や知覚的な材質が保たれる保証ではない。パレットのLの順序を逆転させる変更は今回試していない。固定残差は極端な変更でLを範囲外に出す可能性もある。
4. **色域変換と時間**。今回の4枚・台本ではLの範囲外は0だが、彩度圧縮は発生した。飽和色と、パレット色が近づく・交差する台本、原寸の細線で追加検証する必要がある。今回のGと局所最大は192px幅の標本で、全解像度・すべての台本のちらつき不在を保証しない。
5. **台本の意味**。写真の夕日は色相回転だけでは自然な夜にならない。太陽、窓、反射の役割を保つ必要がある。にせのドット絵でも看板は発光感を失う。画像の種類や、明るい色を固定する指定に応じて既定の台本を分けるべきである。
6. **本物のドット絵**。今回の画像は格子が不均一で色数も多く、インデックス色編集の検証にならない。本物の限定色画像なら元のインデックスを保つ方式を別に持つ判断が必要。
7. **メモリと端末差**。比較を簡単にするため全方式が共通のテクスチャを保持している。約1.57MPでGPUデータは1枚あたり72MiB、4枚で約288MiB。CPUにも同じ前処理配列と元画像を保持する。hard/residualの製品実装なら重み2枚を省ける。大画像・モバイル向けの半精度化・重みの圧縮・単一コンテキスト化は未検証。

## 検査と依存

最終実行の `checks.json` では、必須撮影72枚、ブラウザ実行時エラー0、失敗リクエスト0。外部リクエストは撮影側でも遮断し、記録された104レスポンスはすべてループバックだった。GPU出力を、各候補・各画像のbについて257画素のCPU参照計算と照合し、RGBチャンネルの誤差は最大1。残差2方式のaは全画素で誤差0。b操作、再生時間の進行、390px幅でページ全体のはみ出しがないことも検査した。

ブラウザ内の実行に外部ライブラリは使わない。CDN・Webフォント・外部APIも使わない。数式とWeb APIを自前で実装した。
