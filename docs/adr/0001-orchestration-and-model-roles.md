# ADR-0001: オーケストレーションとモデルの役割分担

- 状態: 承認（モデル調査と試走の結果を受けて確定。試走は各モデル1回なので、本番タスクの結果で見直す）
- 日付: 2026-10-27

## 文脈

- 利用者は Claude の使用量を抑えたい。そのため実装は Orca を通して他のモデルに振ってよい、と指示している。使ってよいと名前が挙がったモデルは、Codex の `gpt-6.1-sol`（推論の強さ xhigh か max）と、dsh（Command Code 経由）の `xiaomi/mimo-v2.6-pro` と `deepseek/deepseek-v4.1-flash`。
- 調査（imozuru）は Claude のサブエージェントで行ってよい、と利用者が指示している。
- 設計と品質保証の責任はメイン（Claude）が持つ。
- 手元で確かめた事実（2026-10-27）:
  - Orca 1.4.240。`orchestration worker-start` は `--agent codex --model <id> --effort <level>` を受け付ける。
  - Codex のモデル一覧に `gpt-6.1-sol` があり、推論の強さは low〜ultra を選べる。
  - dsh は Orca から `--model` を渡せない。起動時のモデルは `~/.dsh-tui/model.json` で決まる。そのため、起動の直前に model.json を書き換え、起動後に画面下のモデル名で確かめる。
  - dsh で使う DeepSeek は `deepseek/deepseek-v4.1-flash`（利用者の指定。公式の latest が 1017 版であることを利用者が確認済み）。MiMo は `xiaomi/mimo-v2.6-pro`。
  - Orca から dsh を起動すると、プロンプトが入力欄に入ったまま送信されないことがある（2回とも起きた）。起動後に `orca terminal send --terminal <handle> --enter` で送信する。読み込み中（画面下に「Checking…」が出ている間）の Enter は効かないので、モデル名の行に `Full access` が出てから送り、画面で送信されたことを確かめる。
  - Codex CLI の更新案内（`agent-update-prompt`）が出ると、Orca からの起動が止まる。`~/.codex/version.json` の `dismissed_version` を最新版にすると出なくなる（案内で「スキップ」を選ぶのと同じ）。
  - コーディネーターの端末は、一度に1つの Run にしか結び付かない。`run-create` で新しい Run を作ると、古い Run の受信箱は `consumer_fenced` で読めなくなる（`run-use` で付け替えはできる）。生きているワーカーがいる間は Run を増やさず、1つの Run に Task を足していく。
  - dsh-tui の headless 実行（`dsh-tui run`）は手元で失敗した（`TASK_FAILED: DSH exited unsuccessfully (1)`）。Orca の TUI 経由で使う。
- 試走（`experiments/model-probe/RESULTS.md`）:
  - 3モデルとも、色の計算の正しさ・60fps・reduced motion・点滅なしの要件を満たした。
  - 見た目の仕上がりは Codex が明らかに上。MiMo は灰色がかった低彩度、DeepSeek は塊の境目が灰色に濁った。
  - 自分で画面を見て直せたのは Codex だけ。dsh の2モデルは、公式には画像入力に対応している（`docs/research/model-survey.md`）が、dsh 経由では画像を読めなかった。
- モデル調査（`docs/research/model-survey.md`）: 100万トークンあたりの料金（入力/出力）は Sol が $2/$10、MiMo が $0.435/$0.87、DeepSeek が $0.30/$1.20（いずれも公式）。

## 決定

振り分けの軸は2本（2026-10-27 に利用者と合意）。**視覚的センスが要るか**と、**技術的にどれだけ難しいか**。

| 仕事の性質 | 担当 | 備考 |
|---|---|---|
| 設計・ADR・タスク分解・レビュー・受け入れ・コミット | メイン（Claude Opus） | 大きな実装は自分でしない |
| **視覚的センスが要る仕事**: アートディレクション、色の台本の数値と既定の時間設計、見本の絵のプロンプトと選定、外枠の UI の視覚設計、見た目の受け入れ判断、最後の仕上げ | Claude。メインが自分で手を動かす。手が足りなければ Claude のサブエージェント | 利用者の判断「デザイン的・視覚的センスは Claude が一番優れている」による。調整は、数値の小さな書き換えと画面の確認を繰り返す |
| 視覚に関係が薄く、**難しい**仕事: エンジン、シェーダー、色の計算の中核、書き出しの中核、難しい試作 | Codex `gpt-6.1-sol`、推論は xhigh | 試走と試作で、自分の画面を見て直せること、検証の手堅さが確かめられた |
| 視覚に関係が薄く、**中くらい〜易しい**仕事: ツール、テスト、データ処理、整理、リファクタリング | dsh `xiaomi/mimo-v2.6-pro` か `deepseek/deepseek-v4.1-flash` | 安い。dsh 経由では画像を読めないので、見た目の確認はメインが `tools/visual-qa` で引き受ける |
| 調査（imozuru） | Claude のサブエージェント（親は Sonnet） | 原文は `~/research/<話題>/`。Claude の WebSearch が上限に届いたら、Codex に同じ手順で引き継ぐ |
| 案出しの発散 | 3モデルを並べる | 好みの違いをそのまま材料にする |

例: 役割ごとの台本では、台本を再生するエンジンは Codex が作り、台本の色と時間の数値はメインが決める。

### 実装の段階の体制（2026-10-27 追記、利用者の提案）

dsh は遅い（光過敏の判定器に約50分）。そこで、dsh には詰め切った易しい Task だけを渡し、詰める仕事は別のエージェントが持つ。メインは「オーケストレーションのオーケストレーション」をする。

| 層 | 担当 | すること |
|---|---|---|
| メイン | Claude Opus（このセッション） | 流れ（ワークツリー）ごとに adviser を立てる。判断が割れたときに裁定する。視覚の判断を持つ。最終の受け入れとコミット |
| adviser（流れごとに1人、その流れのワークツリーに付く） | 技術の流れは Codex（sol）、視覚の流れは Claude | Task を細かく切り、仕様と受け入れの基準を詰め、dsh の成果を一次レビューする。切るのが二度手間か、難しい部分は自分で実装する |
| 実行 | dsh（MiMo / DeepSeek） | 詰め切られた易しい Task だけ |

- adviser は Orca のワーカーとして立てる（`worker-start --worktree new-child` で専用のワークツリー）。**`--base-branch surumenDD/main` を必ず付ける**。付けないと、リポジトリの `main`（最初のコミット）から作られ、メインの作業が見えない（2026-10-27 の M1 で起きた。adviser に早送りさせて直した）。Orca では、ワーカーが自分の手伝いを `worker-start --spec` で起動でき、手伝いはそのワーカーに報告する。
- Claude のサブエージェントは、メインと同じ端末で動くので、独立した Orca の調整役にはなれない（Run の結び付けがぶつかる）。Orca を使わない設計や仕様づくりの adviser として使う。
- dsh の起動は `tools/orca/dsh-launch.sh` で行う。モデルの設定ファイルは機械全体で1つなので、ロックで同時に1つしか起動しない。プロンプトの送信も確かめる。
- 入れ子の深さには上限がある（`nested_worker_depth_exceeded`）。最初の実装の流れで確かめる。
- 「切るのが二度手間」の目安: 仕様を書く量が実装の量と変わらないもの。
- M1 で分かったこと（`app/reports/M1-report.md`）:
  - 入れ子の起動は深さ 2 で動いた（メイン → adviser の Codex → dsh）。
  - dsh に向くのは、API・基準値・入力・許容差・持ち場のファイルを先に固定できる Task。色と Shepard の単体テストは、DeepSeek が 3分7秒で、差し戻しなく終えた。
  - データの型、テクスチャの配置、時計、取り消しのように互いに結び付く部分は、adviser がまとめて書くほうが説明の重複が少ない。
  - 同じ adviser の端末を次の段に再利用できる（M1 → M2）。`worker-start --task <id> --terminal <handle>` に、ワークツリーを `--worktree id:<repo-id>::<path>` の形で渡す。`path:` の形では「認識できるエージェントが動いていない」で断られた。
  - adviser は、メインの判断が要る点（Shepard での L の範囲外）を、数値を勝手に変えずに報告して回した。比較の基準（v2 の台本）を固定データとして凍結し、メインの変更で検査の基準が動かないようにした。

- タスクは Orca の Run・Task・Dispatch で管理し、仕様には Target・Change・Constraints・Ownership・Observable acceptance を必ず書く。
- 仕様には次の2点も入れる。「起動したサーバーやバックグラウンドの処理は止めてから完了報告する」「作業ツリーに範囲外のファイルができたら消さずに報告する」。
- ワーカーの `worker_done` を受けたら、メインが差分と実物（`tools/visual-qa` の結果、スクリーンショット、テスト結果）を見てから受け入れる。報告の文面だけで受け入れない。
- 画面を持つ段の受け入れでは、メインが**配る成果物（ビルドしたもの）を自分で開いて操作し**、コンソールのエラーと、操作の結果の画素を確かめる。ワーカーのテストと画面写真だけで受け入れない。M2 では、adviser の数値の検査はすべて合格だったが、メインが dist を開いて、和文フォントの一部が CSP で拒否される不具合（42件、テストがコンソールを見ていなかった）を見つけた。同時に「島を選んでも絵が暗くならない」とも報告したが、これはメインの見誤りだった。画素を測ると暗くなっていた（線形で 0.38 倍）。ただ、見誤るほど強調が弱かったので、設計を改めた（`docs/design/ui.md`、彩度で沈める）。見た目の判断も、縮小した写真の印象だけでなく画素で確かめる。
- 1つの Task が、視覚的センスの要る部分と要らない部分の両方を含むときは、Task を分ける。前者はメインが持つ。

## 理由

- 使用量を分散しつつ、判断と品質の責任を1か所に置くため。
- 実装を任せる先は、ベンチマークの数字より、このプロジェクトに近い課題での実際の出来で選ぶほうが確か。試走で差が大きかったのは見た目と自己確認の能力で、計算の正しさには差が無かった。
- 美的な判断は、作品の質を最後に決める。だから、それを最も得意とする Claude（利用者の判断）が自分で持つ。技術の仕事は、難しさに応じて Codex と安い dsh に振り分け、使用量を抑える。

## 結果

- 良い点: Claude の使用量が設計とレビューに集中する。モデルごとの得意・不得意が記録に残る。
- 悪い点: 受け渡しの手間と、仕様の書き漏れによる手戻りが増える。メインのレビューが品質のボトルネックになる。
- 見直す条件: あるモデルの差し戻しが続いたとき。dsh で画像入力が使えるようになったとき（MiMo の見た目の仕事を再試験する）。Codex の使用量が上限に近づいたとき。

## 検討した他の案

- すべて Claude で実装する: 使用量の制約に反する。
- モデルを固定せず毎回選ぶ: 比べる根拠が残らない。
