# ADR-0005: 書き出し — WebCodecs で MP4 を主にする

- 状態: 承認（Firefox と Safari の実機確認は、公開前の品質確認で行う）
- 日付: 2026-10-27

## 文脈

- ADR-0003 の未知2「ブラウザだけで、ループする動画と GIF を十分な質で書き出せるか」を、`experiments/export-spike/` で確かめた（dsh DeepSeek）。
- 試作の結果（`experiments/export-spike/NOTES.md`、ffprobe の値はメインが確認）:
  - 時刻を1コマずつ進めて描いたフレームを WebCodecs で符号化した。1080p・8秒・30fps の H.264 は、0.61 秒（実時間の13倍速）で 6.59MB、PSNR 42.83 dB。
  - VP9 は H.264 より約2割小さい。GIF（960×540、20fps）は 3.69MB で、720p の MP4 より大きい。GIF のパレットはコマごとに作るほうが、全体で1つにするより PSNR が 4 dB 高い。
  - 描画は決定的で、2回の書き出しがバイト数まで一致した。ループの継ぎ目の差は、隣り合うコマの差と同程度だった。
  - WebCodecs の映像の符号化は Chrome / Edge 94、Firefox 130（デスクトップ）、Safari 16.4 から使える（出典は同 NOTES）。Safari の VP9 の符号化は確認できていない。H.264 は偶数の大きさが必須。
  - 使ったライブラリはすべて MIT: `mp4-muxer` 5.2.2、`webm-muxer` 5.1.4、`gifenc` 1.0.3。

## 決定

1. 書き出しは、実時間の録画ではなく、**時刻を1コマずつ進めて描いたフレームを符号化する**。同じ設定なら同じファイルが出る。
2. 形式は **MP4（H.264）を主**にする。WebM（VP9）は軽さが要るときの代替。GIF は最後の手段で、パレットはコマごとに作る。
3. 端末が形式に対応しているかは、`VideoEncoder.isConfigSupported()` で確かめてから選ぶ。対応していなければ H.264 にフォールバックする。
4. 書き出す前に、光過敏の判定（ADR-0006 で決める）を通す。
5. マルチプレクサは、試作と同じ MIT のライブラリから始める。Mediabunny への移行は、製品化の段階で改めて判断する。

## 理由

- MP4（H.264）は、符号化が速く、どの主要ブラウザでも作れて、共有先でもそのまま再生できる。
- 決定的に描けば、ループの継ぎ目がずれず、検査と書き出しの結果が一致する。

## 結果

- 良い点: サーバーなしで、端末の中だけで書き出せる（画像を外に送らない約束を守れる）。
- 悪い点: GIF は大きく、色も落ちる。Safari と Firefox の実機確認がまだない。
- 見直す条件: Safari / Firefox の実機で失敗したとき。書き出しの時間が長い絵（大きな画像、長いループ）で問題になったとき。

## 検討した他の案

- MediaRecorder による実時間の録画: フレーム落ちと継ぎ目のずれが起きうる。検査と結果が一致しない。
- サーバーでの符号化: 画像を端末の外に送らない約束（ADR-0003）に反する。
